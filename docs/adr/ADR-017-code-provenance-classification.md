# ADR-017: Code Provenance Classification — Human / AI-Assisted / AI-Generated

**Status:** Accepted  
**Date:** 2026-06-17  
**Deciders:** cargo-cicd core team, Vision 2030 architecture committee  
**Tags:** provenance, ai-attribution, code-classification, regulatory, supply-chain

---

## Context

The software industry in 2026 faces a new and rapidly evolving challenge: a significant and growing fraction of production code is generated, co-authored, or substantially influenced by AI language models (LLMs). This creates accountability and regulatory questions:

1. **Regulatory accountability**: Frameworks like DO-178C and FDA 21 CFR Part 11 require documented evidence of human review and approval for safety-critical software. AI-generated code that is not explicitly reviewed presents a compliance gap.

2. **Supply chain transparency**: Downstream consumers of a library may have policies about AI-generated code (training data licensing concerns, quality requirements, organizational prohibitions). Without provenance metadata, they cannot make informed decisions.

3. **Quality baseline differences**: Empirical research (2024-2026) shows that AI-generated code has different defect distributions than human-written code — different failure modes, different patterns of security vulnerabilities, different test coverage needs. Provenance classification enables risk-stratified review.

4. **Academic and legal context**: Several jurisdictions are developing regulations around AI-generated software (EU AI Act 2025, proposed US AI Accountability Act). Supply chain tooling needs to be ready to report provenance when required.

5. **Organizational policies**: Many organizations are implementing internal policies about AI code review thresholds. tooling that doesn't track provenance cannot enforce these policies.

### Classification Categories

Three levels of human involvement are defined:

**Human**: Code written by a human without AI assistance. The developer typed the code, made design decisions, and is fully accountable for the content.

**AI-Assisted**: Code where a human made the design decisions and overall structure, but used AI tools (GitHub Copilot, Claude, Cursor, etc.) for completions, boilerplate generation, or minor suggestions. The human reviewed and approved every line. The human is accountable; AI was a productivity tool.

**AI-Generated**: Code produced by an AI model in response to a prompt, with the human serving primarily as editor/reviewer rather than author. The human may have reviewed and approved, but the AI was the primary author of the logic. Accountability is shared; additional review may be warranted.

### Detection Challenges

Reliable automated classification is technically very difficult:

1. **Heuristic detection**: Certain code patterns are statistically associated with AI generation (uniform comment density, specific idiom choices, unusual verbosity in docstrings, characteristic indentation patterns). These have significant false positive and false negative rates.

2. **Git metadata**: Some AI tools leave metadata in commits (GitHub Copilot suggestions, Claude Code Co-Authored-By trailers). This is partial evidence but not universal.

3. **Model watermarking**: Some AI providers embed statistical watermarks in generated text. These are not reliable for code and can be stripped.

4. **Explicit declaration**: The developer or CI system explicitly declares the provenance. This is authoritative but relies on honesty and compliance.

## Decision

**Classify source files by provenance (Human, AI-Assisted, AI-Generated) using a two-tier approach: heuristic detection as a default, with explicit declaration as the authoritative override. Explicit declaration always wins.**

### Tier 1: Explicit Declaration (Authoritative)

Developers or CI systems declare provenance explicitly via environment variable or file annotation:

**Environment Variable (per session)**:

```bash
# Declare that all files committed in this session are AI-Assisted
export CARGO_CICD_PROVENANCE=AI-Assisted

# Or use the short form
export CARGO_CICD_PROVENANCE=human
export CARGO_CICD_PROVENANCE=ai-generated
```

**File Annotation (per file)**:

```rust
//! # Provenance: AI-Generated
//! 
//! This module was generated by Claude claude-sonnet-4-5 on 2026-06-17.
//! Reviewed and approved by: <developer name>
//! Review date: 2026-06-17
```

The annotation parser in `src/adapters/provenance_detector.rs` looks for the `# Provenance:` comment in the first 10 lines of each `.rs` file:

```rust
pub enum ProvenanceClass {
    Human,
    AiAssisted,
    AiGenerated,
    Unknown,   // No declaration; heuristic applied
}

impl ProvenanceDetector {
    pub fn classify_file(path: &Path) -> ProvenanceClass {
        // 1. Check CARGO_CICD_PROVENANCE env var (session-level override)
        if let Ok(env_val) = std::env::var("CARGO_CICD_PROVENANCE") {
            return ProvenanceClass::from_str(&env_val).unwrap_or(Unknown);
        }
        // 2. Check file annotation (file-level declaration)
        if let Some(class) = Self::read_file_annotation(path) {
            return class;
        }
        // 3. Fall back to heuristic
        Self::heuristic_classify(path)
    }
}
```

### Tier 2: Heuristic Detection (Default, Low Confidence)

When no explicit declaration is present, heuristics are applied. Heuristics produce a `ProvenanceClass` with a confidence score:

```rust
pub struct HeuristicResult {
    pub class: ProvenanceClass,
    pub confidence: f32,   // 0.0 = random guess, 1.0 = certain
    pub signals: Vec<HeuristicSignal>,
}
```

**Heuristic signals** (with approximate empirical weights):

| Signal | Weight | Notes |
|--------|--------|-------|
| `Co-Authored-By: Claude` in git log | 0.9 | Strong AI authorship signal |
| `Co-Authored-By: GitHub Copilot` in git log | 0.85 | Strong AI authorship signal |
| Comment-to-code ratio > 0.4 | 0.4 | AI tends to over-comment |
| Docstring on every public item | 0.3 | AI-generated code is often thoroughly documented |
| Consistent snake_case + verbose naming | 0.2 | AI naming convention patterns |
| No `TODO`, `FIXME`, `HACK` comments | 0.2 | AI less likely to leave these |
| `unwrap()` density < 0.05 | 0.25 | AI avoids unwrap more than humans |
| `expect()` with meaningful messages on every call | 0.3 | AI characteristic |

When confidence < 0.6, the classification is `Unknown` rather than a low-confidence guess. The `status show` verb reports `Unknown` provenance files as a warning when the `process-data` feature is enabled.

### Provenance in ProcessEvent

ProvenanceClass is recorded in the ProcessEvent for the relevant command:

```rust
pub struct ProcessEvent {
    // ...existing fields...
    pub provenance_class: Option<ProvenanceClass>,      // For code-producing events
    pub provenance_confidence: Option<f32>,             // Heuristic confidence, if applicable
    pub provenance_evidence: Vec<String>,               // Signals that produced the classification
}
```

For commands that don't produce code (status show, target prune), provenance is `None`.

## Limitations

### Heuristic Limitations

1. **False positives**: A human who writes thorough documentation will be misclassified as AI-generated. These require explicit overrides.

2. **False negatives**: AI-generated code that mimics human style (minimal comments, deliberate shortcomings) will be classified as Human. There is no reliable counter-measure.

3. **Tool evolution**: As AI code generation tools evolve, the heuristic signals become less reliable. The heuristics are calibrated for 2026 LLM output patterns.

4. **Training data contamination**: LLMs trained on large code corpora may produce code that is statistically identical to specific human authors' styles.

### Why Explicit Declaration is Authoritative

Given the heuristic limitations, explicit declaration is the only reliable mechanism. The system is designed to:

1. Make explicit declaration easy (one env var or one comment).
2. Make missing declaration visible (Unknown provenance is a warning).
3. Never silently assume Human provenance (Unknown is not Human).
4. Trust the developer's declaration (honesty enforcement is a process/policy problem, not a technical problem).

---

## Consequences

### Positive

1. **Regulatory readiness**: When DO-178C or FDA 21 CFR Part 11 mandates provenance declaration, cargo-cicd is already tracking it. The XES evidence includes provenance data that auditors can inspect.

2. **Organizational policy enforcement**: CI/CD pipelines can fail if AI-Generated files exceed a configured threshold or lack explicit human review declarations.

3. **Supply chain transparency**: Downstream consumers can inspect published crate evidence to understand the provenance breakdown.

4. **Risk-stratified review**: Code review workflows can flag AI-Generated files for additional scrutiny.

5. **Research data**: Aggregate provenance statistics across the crates.io ecosystem will inform research on AI-assisted software quality.

### Negative

1. **False positives are disruptive**: Human-authored code classified as AI-Generated may trigger unnecessary reviews or policy failures. Mitigation: Heuristics are advisory; only explicit declarations are used for policy enforcement.

2. **Friction for honest disclosure**: Requiring provenance declaration adds friction to development. Developers may resist or use incorrect classifications to avoid the overhead. Mitigation: Default to Unknown rather than penalizing non-declaration; Unknown is a warning, not a failure.

3. **Gaming**: Developers who want to avoid AI-Generated classifications can add `//! # Provenance: Human` regardless of actual provenance. There is no technical enforcement against dishonest declaration. Mitigation: Policy enforcement, code review, and organizational accountability.
